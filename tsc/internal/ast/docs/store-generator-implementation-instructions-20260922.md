## 0. 作るものの性格

設計文書 §6 の TODO 7 の前半 (7a)。**本物の generator と本物の Store package** を作る。storeexp との違い:

| | storeexp | 7a |
| --- | --- | --- |
| generator | Go の書き捨て (`_gen/main.go`) | `tools/scripts/tsc/generate-go-store.ts`。`generate.ts` から呼ぶ |
| 入力 | `ast.json` + Go の型情報 | `ast.json` だけ (`schema.ts` の `api` を使う) |
| typed view と accessor | 代表 7 kind を手書き | 全 kind を生成 |
| data word | Identifier の text だけ | 全 kind の非 child member |
| 構築 | shape 駆動の汎用 builder | kind ごとの生成 constructor |
| build tag | `storeexp` | なし (production の package。ただしどこからも import されない) |
| 配置 | `internal/ast/storeexp` | `internal/ast/store` (package `store`) |

まだ作らないもの (7b 以降): parser の直接構築、scratch と Compact、binder / checker / emit / LSP との結合、symbol / locals / flow の列、synth Store、JSDoc の置き場所。

## 1. ガード

1. package は `tsc/internal/ast/store`、package 名は `store`。`internal/ast` を import してよい (`ast.Kind`、`ast.NodeFlags`、`ast.ModifierFlags`、`ast.TokenFlags`、`ast.ModifierToFlag`)。**`internal/ast` から `store` を import しない。** production の package から `store` を import しない。

5. `doc.go` の package comment (英語) に: 設計文書へのパス、この package が Store AST の本体であること、7a の範囲 (parser 未結合)、`storeexp` との関係 (置き換える)。

## 3. 型と API (`store.go`)

storeexp の `store.go` をそのまま出発点にする。設計文書 §2.1、§2.3、§2.5 のとおりで、名前と形を変えない。storeexp からの差分:

- `Store.Root()` は残す (post-order なので最後のノード)。
- **list の nil ガード。** `visitList` は呼ぶ側で `at != 0` を検査してから呼ぶ (設計文書 §2.3、storeexp の最終形)。`List` の `Len` / `Pos` / `End` は番兵 block (`extra[0:3] = 0`) で nil でも読めるままにする。
- slot の添字は `int(h.data)+k` で足す (`uint32` の切り詰め `MOVW` を消す。設計文書 §2.5 の再検討 2)。
- `List.Refs()` は storeexp のまま (`unsafe.Slice`)。**`unsafe` は `Ref()` と `Refs()` の 2 箇所だけ。** bounds check を消す形 (`*[1<<32]NodeHeader` など) は却下済み (設計文書 §2.5 の再検討 3)。書かない。
- `modifierFlags` と `uint16` 切り詰めの TODO コメントは storeexp と同じものを置く。
- `Text()` の text は §5 の形。
- Builder は append ベースのままでよい (scratch / Compact は 7b)。ただし **`Finish` の後にだけ `Node` を配る** 契約と「id で書く」規則は守る。

## 4. generator (`generate-go-store.ts`)

`schema.ts` の `api` を使う。`api.nodes()` の各 `NodeType` について `node.members` を **宣言順** に見て、`MemberInfo` で分類する。`generate-go-ast.ts` の `schemaMembers` (`noFactory` を除く) は使わない。使うのは下の表の分類である。

### 4.1 member の分類

| 条件 (この順に判定) | 扱い |
| --- | --- |
| `m.isKindParam()` | header の kind。slot なし |
| `m.name === "Flags"` (inherited、NodeBase) | header の flags。slot なし |
| `m.name === "modifierFlags"` (noGo) | header の modifierFlags。slot なし |
| `m.goOnly` (Symbol、LocalSymbol、Locals、NextContainer、facts、FlowNode、ReturnFlowNode、EndFlowNode、FallthroughFlowNode) | slot なし。設計文書 §5 の side table |
| `m.noGo` | slot なし |
| `m.isChild()` かつ `m.listKind` あり | **list slot** (NodeList / ModifierList / raw)。1 word = block index |
| `m.isChild()` | **child slot**。1 word = NodeRef |
| `m.type` が primitive `string` かつ `m.listKind === "raw"` (JSDocCommentBase の `text`) | **slot なし、TODO コメント** (JSDoc の置き場所は設計文書 §5 で未決) |
| `m.type` が primitive `string` | **text**。Identifier / PrivateIdentifier は header の `data` (§5)。それ以外は data word 2 つ `[off, len]` |
| `m.type` が primitive `bool` | data word 1 つ (0 / 1) |
| `m.type` が primitive `TokenFlags` | data word 1 つ |
| `m.type` が kind 型 (`Operator`、`Token`、`Keyword`、`KeywordToken`: `SyntaxKind.*` の配列) | data word 1 つ (`uint32(ast.Kind)`) |
| それ以外 | generator が member 名と型を列挙して失敗する |

slot の並びは宣言順で、child / list / data word を分けない (設計文書 §2.2)。slot 数は 16 以下 (list mask が `uint16`。超えたら失敗)。定義の無い kind (token、keyword、`instantiationAliases` で作られる kind) は slot 0。

### 4.2 override 表 (generator 内のデータ)

storeexp と同じ:

- member 順: `SourceFile` は `[Statements, EndOfFileToken]`、`JSDocParameterOrPropertyTag` は `[TagName, name, IsBracketed, TypeExpression, IsNameFirst, Comment]` (宣言順。Pointer 版は `IsNameFirst` で順序を実行時に変えるが固定 shape では表せない。**TODO コメント**を置き、設計文書 §7 の未決事項に足す)。
- 役割表から除外: `Expression` から `DefaultClause`、`TypeParameter`、`SyntheticReferenceExpression` (Pointer の `(*Node).Expression()` が panic する kind)。
- §7 の等価テストで新たに合わない kind が出たら、override 表に足す。accessor や walker の側で特別扱いしない。

### 4.3 出力

**`shapes_generated.go`**: storeexp と同じ `shape{slots uint8; listMask uint16}` の `[512]shape`、役割 slot 表。役割表は **member 名が 2 つ以上の定義に現れる child / list / text member** の全部について作る (`nameSlot`、`expressionSlot`、`typeSlot`、`initializerSlot`、`bodySlot`、`modifiersSlot`、`textSlot`、`statementsSlot`、`membersSlot`、`typeParametersSlot`、`parametersSlot`、`typeArgumentsSlot`、`argumentsSlot`、`tagNameSlot`、… generator が列挙する)。`0xFF` = 不在。`init` 関数で埋める形 (storeexp の `roleSlots()`) でよい。Kind の最大値が 512 未満であることを generator が検査する。

**`views_generated.go`**:

- slot 定数: kind ごとに `const ( callExpressionExpressionSlot = iota; … )`。未 export。
- typed view: 定義ごとに `type CallExpression struct{ s *Store; h *NodeHeader }` と `func (n Node) AsCallExpression() CallExpression` (`storeChecks` の assert 付き。多 kind の定義は kind の集合で assert)。
- member accessor: child → `Node`、list → `List`、text → `string`、bool → `bool`、TokenFlags → `ast.TokenFlags`、kind 型 → `ast.Kind`。名前は member 名を capitalize (`name` → `Name`、`modifiers` → `Modifiers`)。形は storeexp の `views.go` と同じ 1 行。
- 役割 accessor: `func (n Node) Name() Node` など、役割表ごとに 1 つ。storeexp の形 (表引き → `0xFF` なら `n.s.node(0)` / nil `List` / `""`)。`Text()` は役割表 `textSlot` で引き、Identifier / PrivateIdentifier だけ header の `data` を使う分岐を持つ (§5)。
- `IsXxx` 述語は作らない (Pointer の `IsXxx` は `Kind ==` の比較で、`n.Kind() == ast.KindXxx` を書けばよい)。

**`foreach_generated.go`**: storeexp と同じ。Kind の数値順の 1 本の switch、kind 別関数、child は `if ref := NodeRef(s.extra[data+k]); ref != 0 && v(s.node(ref))`、list は `if at := s.extra[data+k]; at != 0 && visitList(s, at, v)`。`visitList` は手書き (`store.go`) で cost 80 以下を保つ (検証で確認する)。

**`builder_generated.go`**: 定義ごとに 1 つ:

```go
func (b *Builder) NewCallExpression(flags ast.NodeFlags, pos, end int32,
    expression NodeRef, questionDotToken NodeRef, typeArguments uint32, arguments uint32) NodeRef
```

- 引数は slot 順。child は `NodeRef`、list は block index (`uint32`)、text は `string`、bool は `bool`、TokenFlags は `ast.TokenFlags`、kind 型は `ast.Kind`。多 kind の定義は先頭に `kind ast.Kind` を取る。
- 本体: payload を `extra` に追記 (text は §5 の形に変換)、header を追記、**子の `parent` を書く** (child slot と list の全要素。設計文書 §2.7)。
- **`modifierFlags`**: `modifiers` slot を持つ kind は、block の要素の kind から `ast.ModifierToFlag` で OR を取って header に置く (`ast.ModifiersToFlags` は `[]*Node` を取るので使えない)。持たない kind は 0。
- token / keyword (slot 0 の kind): 手書きの `func (b *Builder) NewToken(kind ast.Kind, flags ast.NodeFlags, pos, end int32) NodeRef` を `store.go` に置く。
- `Identifier` / `PrivateIdentifier`: `NewIdentifier(flags, pos, end, text string)`。§5 の形。
- `List(pos, end int32, elems []NodeRef) uint32` は手書き (storeexp と同じ)。

**`convert/convert_generated.go`**: `package convert`、`func Convert(file *ast.SourceFile, fileIndex uint32) *store.Store`。post-order、kind ごとに member を読んで `NewXxx` を呼ぶ。private member は公開 accessor (`Name()`、`Modifiers()`) で読む。JSDoc は辿らない。`store` の公開 API だけで書く (これが Builder の API の検査になる)。

### 4.4 登録

`generate.ts` の `generate()` に `generateGoStore()` を足す。`node tools/scripts/tsc/generate.ts` と `hereby generate:ast` の両方で生成されること。

## 5. text

設計文書 §2.4 と storeexp の仮決めを、全 kind に広げる。

- **Identifier / PrivateIdentifier**: payload 0。`h.data` = text の開始 offset、`Text()` = `src[data:end]`。source の部分列でないとき (escape 付き識別子) は `texts` に追記し、`extra` に `[off, len]` を置き、`data = 1<<31 | index`。storeexp と同じ。
- **それ以外の text member** (literal の `Text`、`RawText` など): data word 2 つ `[off, len]`。`off` の最上位 bit が 1 なら `texts`、0 なら `src`。constructor は `src[end-len(text):end] == text` なら `src` の offset、違えば `texts` に追記する。**literal の `Text` は cooked (escape 処理済み) なので多くが `texts` に入る。** それでよい (parser が直接構築するときの扱いは 7b で決める)。
- flag の置き場所 (`data` / `off` の最上位 bit) は仮決めのまま。コメントに明記する。

## 6. Kind と shape の制約

- `ast.Kind` の最大値 < 512。generator が `kinds.elements` の数で検査する (380)。
- slot 数 ≤ 16。
- `unsafe.Sizeof(NodeHeader{}) == 24` をテストで固定。

## 7. テスト

**`store_test.go` (手書き)**:

1. fingerprint: `fixtures.ASTBenchFixtures` を `convert.Convert` して preorder の `kind|pos|end` の sha256 と訪問数が `internal/ast/ast_benchmark_test.go` の `astBenchmarkBaselines` と一致 (storeexp と同じリテラル)。
2. small walk: `TestASTBenchmarkSmallWalk` と同じ source で同じ列。
3. escape 付き識別子と、`texts` に入る literal の `Text()`。
4. `NodeHeader` の size、`Ref()` の往復、Kind < 512。
5. **corpus**: `internal/parser/parser_test.go` の `FuzzParse` の seed と同じ集め方 (`testdata/fixtures` 以下の全 parsable file と、`testdata/tests/cases/{compiler,conformance}` を `testrunner.ParseTestFilesAndSymlinks` で分解したもの。無ければ skip) で、全ファイルを parse → Convert → 生成の等価テスト (下) を流す。JSX、template、escape、JS を含む。時間がかかるなら `-short` で `fixtures` だけにする。

**`equivalence_generated_test.go` (生成)**: Pointer と Store を同時に preorder で辿り、全ノードで:

- kind、pos、end、flags、`ModifierFlags() & 0xFFFF`、親の kind と pos、`Ref()` の往復。
- **定義ごとに全 member** を typed view で比較 (child: kind と pos、不在は両方 nil。list: `Len` / `Pos` / `End` と各要素。text: 文字列。bool / TokenFlags / kind 型: 値)。
- 役割 accessor: `Name`、`Expression`、`Type`、`Initializer`、`Body`、`Text`、`Modifiers` を Pointer の同名メソッドと比較 (Store の表が `0xFF` でない kind だけ。Pointer が panic する kind は storeexp の `role` と同じ recover で検出)。
- 不一致は storeexp の `mismatches` と同じく kind と label で集計して 1 回で全部出す。

全テストを tag なしと `-tags storechecks` の両方で通す。
