## 0. 作るものの性格

7d-2 は 2a 変換 / 2b 等価 / 2c 性能の 3 小段に分ける (残りの設計 §4)。**2a は checker と printer を Store に変換して、build が通る状態にする。** checker はまだ動かさない (checker の等価は 2b、性能は 2c)。2a で確かめるのは、checker 無しで閉じる 2 つの単体等価 (nameresolver、printer) と、既存の parse / bind が変わらないこと。

| | 7d-1 まで | 2a |
| --- | --- | --- |
| 変換器 (`tools/cmd/storetranslate`) | ast の utility を到達計算で `store/utilities.go` に出す。binder.go は試作だけ | 複数の package を変換し、method・型・interface を扱う。到達計算は checker の根から (残りの設計 §2.2) |
| checker | Pointer だけ | `storechecker` を生成してコミット (P2 は手書き) |
| 印字 | — | printer を `storeprinter` に変換 (NB1'、残りの設計 §2.4)。Store → Pointer の変換器は作らない |
| nameresolver | — | binder/nameresolver.go を `storebinder` に変換 |

作らないもの: H1 のハーネス (`storechecker.Program` の実装)、Q1 の比較、symbol の一対一対応の比較器、private の lookup の試験 (2b)、Check KPC の driver、Pointer AST を持たない retained / GC の測定、印字の全区間の計測、合成の Store の数の計測 (2c)。

## 3. 変換器

### 3.1 対象 package と出力

| Pointer | Store | 出すもの |
| --- | --- | --- |
| `ast` | `store` (既存) | 到達した package-level 関数を `utilities.go` に (7d-0 と同じ)。`visitor.go` と `diagnostic.go` は file 単位で全部 |
| `checker` | `storechecker` | 到達した関数・method と、§3.2 の型・定数・変数 |
| `printer` | `storeprinter` | 同上 |
| `binder` | `storebinder` (既存、手書き) | `nameresolver.go` だけを file 単位で。ほかの binder の関数は storebinder の手書きの同名関数を呼ぶ |
| `evaluator` | `storeevaluator` | 全部 (168 行) |
| `scanner`、`nodebuilder`、`pseudochecker`、`modulespecifiers` | `store` + 同名 | 到達したもののうち、signature か本体か型が §3.3 で変わる型を含むものだけ。含まないものは元の package を呼ぶ (例: `scanner.IsIdentifierText` はそのまま) |

- 出力は元の file ごとに同じ名前の file に、元の宣言の順序・名前・comment を保って出す (7d-0 と同じ)。到達した宣言が 1 つも無い file は出さない。
- package の境界をまたぐ参照 (`binder.X` → `storebinder.X` など) は、行き先の package に同名の手書きか変換の出力があればそれを、無ければ元の package を呼ぶ。行き先に無いのに型が変わる関数を呼ぶなら problem。
- 試行の再現手順と今の problems は `_store-checker-7d2-survey/` (ignore 対象) にある。試行の `-overlay` のコードは参考で、そのまま使わなくてよい。

### 3.2 到達計算 (残りの設計 §2.2)

- 根: `NewChecker`、`(*Checker).GetDiagnostics`、`GetSuggestionDiagnostics`、`GetGlobalDiagnostics`、`GetTypeAtLocation`、`GetSymbolAtLocation`、`TypeToString`、`NewNodeBuilder`、`IsTypeAny` (7d 設計 §2.7)。**加えて §6.3 の printer の単体等価が呼ぶ storeprinter の入口 (`NewPrinter` と `(*Printer).Write`) と、§6.2 の nameresolver の単体等価が呼ぶ `(*NameResolver).Resolve`。** 全ての出力 package の `init` 関数も根。package-level の変数と定数は、到達したコードが名指したときに到達とし、その初期化式を辿る (全変数を根にはしない。関数値の表を持つ変数から刈るはずの関数が引き込まれるため)。
- 関数と method の本体 (closure を含む) に現れる識別子を `TypesInfo.Uses` で辿る。static な method の呼び出しと method value は `*types.Func` になる。関数値は名前が現れた時点で到達とする (7d-0 と同じ)。
- **interface**: 到達したコードが名指す interface 型 I と、到達した名前付き型 T (出力 package のもの) について、T か *T が I を満たすなら、I の method に当たる T の method を到達とする。I の method の呼び出しが到達したかは問わない (T を I に代入する箇所があるとコンパイルに全 method が要るため)。
- 型・定数・変数: 到達した宣言が名指す型・定数・変数を到達とし、型の field・method の signature・埋め込みが名指すものも辿る。**storechecker と storeprinter では package-level の型の宣言は全部出す** (checker の型は checker の中で閉じていて、刈っても得るものが少なく、刈り残しの判定を増やすだけ)。関数と method は刈る。
- 変換しない package (compiler、ls、transformers、parser の本体など) の先は辿らない。
- 報告: package と file ごとの到達した関数・method の数と全体の数 (7d 設計 §2.1 の試作の表と同じ形)。

### 3.4 P2

7d-0 と同じ仕組み: 出力 package の `*_manual.go` に同名の関数・method があれば、変換はそれを出さない。**型の宣言にも同じ仕組みを広げる** (`Program` のため): `*_manual.go` に同名の型があれば変換はその型を出さず、hash は Pointer の型の宣言 (`type` から閉じ括弧まで) で取る。各関数の直前に `// storetranslate:pointer-hash <sha256 の先頭 16 桁> <file>:<func>` を書き、変換器が照合して違えば止まる。method の P2 も同じ (`<file>:<Type>.<method>`)。

今の時点で P2 と決まっているもの:

| P2 | 中身 |
| --- | --- |
| R4 の checker の 5 関数 (`checkSourceElements`、`checkTypeParameters`、`reportUnusedVariableDeclarations`、`getEntityNameForDecoratorMetadataFromTypeList`、`getSpreadArgumentIndex`) と、`checkTypeParameters` が引数を渡す `checkTypeParametersNotReferenced` | **List 版を足す。元の関数 (slice を受ける) は通常の変換で残す** (下の「List 版」) |
| `asRecursionId` (relater.go:94、型引数の制約に `*ast.Node` を含む generic) | node は `Key()` を id にする |
| `checkGrammarForUseStrictSimpleParameterList` (grammarchecks.go、`FindUseStrictPrologue` の呼び出し元) | storebinder の `[]NodeRef` 版を呼ぶ |
| `parseIsolatedEntityName` (jsx.go:1435) | `storeparser.ParseIsolatedEntityName(c.program.IDSpace(), name)` を呼ぶ (R16) |
| `NewChecker` | 変換の出力と同じ本体に、region と Factory を作る 2 行を足したもの (§5.1) |
| 型 `Program` (checker.go:554 の interface) | 変換の出力に `IDSpace() *store.IDSpace` を足したもの (§5.1)。**型の宣言の P2** (下) |
| `getNodeBuilderEx` | `storeprinter.NewEmitContextIn(c.factory.Region())` (§5.1) |
| storeprinter の `NewEmitContext`、`NewNodeFactory` | region を受けない版は panic する。region を受ける `NewEmitContextIn` / `NewNodeFactoryIn` を手書き (§5.1) |

**List 版** (2026-09-29 のレビューで追加): 5 関数はどれも、list を渡す呼び出し元と slice を渡す呼び出し元の両方を持つ (`checkSourceElements(elements)`、`checkSourceElements(s.typeArguments)`、`getSpreadArgumentIndex(args)` の 3 箇所、`getEntityNameForDecoratorMetadataFromTypeList([]*ast.Node{TrueType, FalseType})` など)。引数を `store.List` だけにすると slice の呼び出し元が型で合わない。そこで:

- 元の関数は通常の変換で `[]store.Node` を受ける版になる (slice の呼び出し元はそのまま呼ぶ)。
- P2 に **`<名前>List`** (例: `checkSourceElementsList(nodes store.List)`) を足す。本体は元の関数と同じで、引数の型だけが `store.List` (range・index・len は `List` の規則、helper は R4 の List 版)。直前に元の Pointer の関数の hash を `// storetranslate:pointer-hash <hash> <file>:<元の名前>` で書き、上流で元が変われば止まる。`checkTypeParametersList` は `checkTypeParametersNotReferencedList` を呼ぶ (`checkTypeParametersNotReferenced` の呼び出し元は `checkTypeParameters` だけなので、その List 版だけが要る)。
- 呼び出しの規則: 出力 package の関数 F の `[]*ast.Node` の引数に list を渡す箇所は、`<F>List` が P2 にあり、その引数が `store.List` で他の引数が同じ型なら `<F>List` を呼ぶ。無ければ problem。`<F>List` という名前の関数が元から出力 package にあれば problem (名前の衝突)。
- 採らなかった案: 呼び出しの箇所で `List` を `[]store.Node` に写す (呼ぶたびに確保し、statement ごとの `checkSourceElements` の費用が Check ゲートに乗る。残りの設計 §3 の 2 で退けた)、`Len()` / `At()` を持つ interface を引数にする (List を interface に入れるたびに確保し、要素ごとに動的な呼び出し)。

これ以外に変換器が problem を出したら、規則にできるか 1 件ずつ見て、できなければ P2 にする。**P2 の一覧 (関数、行数、理由、規則にしなかった理由) と、出力 package ごとの「変換した関数の数 / P2 の数 / P2 の行数」を報告する。自動化率の線は置かない** (残りの設計 §2.3)。

## 4. 手書きの追加

### 4.1 `store` の Node の method (R2)

Pointer の ast.go の同名の method と同じ意味で、`Node` (と必要なら typed view) に足す。

- list を返すもの: `ModifierNodes()`・`TypeArgumentList()`・`ArgumentList()`・`ElementList()`・`TypeParameterList()`・`StatementList()`・`PropertyList()`・`ParameterList()`・`Decorators()`。生成済みの多相 accessor (`Arguments()` などは既に `List` を返す) を呼ぶ。Pointer の `XxxList()` が `*NodeList` を、`Xxx()` が `[]*Node` を返す組は、Store ではどちらも `List` を返す。
- data の interface を返すもの (`FunctionLikeData`・`ClassLikeData`・`BodyData`・`LocalsContainerData`・`DeclarationData`): Store に data の型は無く、`Node` を返す method にしても `x.FunctionLikeData().Parameters` の field 読みは `Node` に対して書けない。そこで規則にする: `x.XxxData().F` (method の返り値の型が data の interface で、その field F を読む) → `x.F()` (多相 accessor)。`x.XxxData()` を単独で使う箇所 (nil 比較、変数への代入、引数に渡す) は problem にして報告する。method は足さない。
- `IsTypeOnly`・`Attributes`・`GetResolutionModeOverride`・`CanHaveStatements`・`Comments`: Pointer と同じ本体を Store の accessor で書く。
- 試行に出たほかの method (`AsFlowSwitchClauseData`、`FlowNodeData`、`AsFlowReduceLabelData` など flow の data) は、7d-0 の `Flow` の API で表せるなら規則に、表せなければ報告する。

### 4.2 `store.File` の method と field の移行 (R3)

今の `store.File` は `FileName`・`Path`・`Text`・`Imports` を公開の field で持つので、同名の method を足せない。一方、checker の `Program` の interface (checker.go:562〜574) と printer / modulespecifiers の host の interface は `ast.HasFileName` (`FileName()`・`Path()`) を受け、checker はそこに `*ast.SourceFile` を渡す。別名の method を足すだけでは `ast.HasFileName` を満たせない。**そこで 4 つの field を移行する (2026-09-29 のレビューで決定):**

- `FileName`・`Path`・`Text`・`Imports` を小文字の field (`fileName`・`path`・`text`・`imports`) にし、Pointer の `SourceFile` と同じ名前の method `FileName() string`・`Path() tspath.Path`・`Text() string` を足す。`*store.File` は `ast.HasFileName` を満たす。
- `Imports()` は `[]NodeRef` を返す method にする (`Imports() []NodeRef`)。呼び出し側 (checker の `getAlternativeContainingModules`、symbolaccessibility.go:183 / 185 の `len` と range) は R3 の `[]NodeRef` の規則 (要素ごとに `f.Store.Node(r)`) で読み、`[]Node` は作らない (この関数は (symbol, file) の cache miss ごとに走る)。storeparser が書く `AppendImport(ref NodeRef)` を足す。
- 作る側 (storeparser/parser.go:550 の `&store.File{FileName: …, Path: …, Text: …}`) のための constructor か setter を足す (`store.NewFile(fileName, path, text)` など。形は任せ、報告する)。
- 既存の読み書き (storeparser の references.go・jsdoc.go・parser.go、storebinder の binder.go:818 と utilities.go、store の jsdoc.go・テスト、storetest、`_e2e/main.go`) を置き換える。§1 のガードが許すのはこの置き換えだけ。
- 費用: method は inline される 1 load で、field の読みと同じ命令になる見込み。storeparser と storebinder の既存の関数の本体が変わるので、検証が Parse / Bind の KPC を取る。

ほかに足すもの: `ForEachChild(...)`、`Symbol` / `Locals` / `GlobalExports` / `PatternAmbientModules` などの Pointer の field の読み (`Bound` の解決層を読む method。Pointer の field と同名の Store の field が無いので衝突しない)、試行の problems の SourceFile の 14 種 (`_store-checker-7d2-survey/problems.txt`) が全部、この節か R3 の規則で消えること。

### 4.3 そのほか

- `List` 版の helper (R4): `store` の `node_helpers.go` と同じ場所に、`SomeList` など。名前と選び方は 7d-0 の Node 版と揃える。評価順・早期終了・nil の扱いを Pointer の helper と同じにする。

## 5. 生成物の要点

### 5.1 region と Factory (本書で決めたこと)

Pointer の checker は `factory ast.NodeFactory` を zero 値のまま使い、nodebuilder は印字のたびに `printer.NewEmitContext()` で自分の factory を作る。Store の `Factory` は region と容量が要る (7d-0 の R)。

- **checker ごとに 1 つの `NodeRegion`** を `NewChecker` (P2) で `store.NewNodeRegion(program.IDSpace())` として作り、`c.factory = store.NewFactory(region, synthStoreCapacity, store.FactoryHooks{})` を置く。`synthStoreCapacity = 4096` は storechecker の手書きの定数で、残りの設計 §2.5 を指す comment を付ける。**IDSpace は Program から取る** (2026-09-29 のレビューで訂正): root file の無い Program は file が 0 件で (compiler/fileloader.go:185 は root が空なら lib も足さない)、Pointer の `NewChecker` はそれでも正常に終わる。先頭の file から取ると panic する。storechecker の `Program` は Pointer の interface に `IDSpace() *store.IDSpace` を足した型の P2 にし (§3.4)、2b の adapter が実装する。
- nodebuilder の EmitContext と Factory は checker と同じ region に作る (動作設計: region の Factory は checker と nodebuilder が共有し、Store は共有しない)。`getNodeBuilderEx` (P2) が `storeprinter.NewEmitContextIn(c.factory.Region())` を渡す。
- `store.Factory` の zero 値は使えないままにする (region の無い Factory を作らない)。

### 5.2 EmitContext

printer/emitcontext.go の到達分をそのまま変換する (残りの設計 §2.4)。`map[*ast.Node]…` と `core.LinkStore[*ast.Node, …]` は L1 と R5 の規則で `NodeKey` の key になる。`textSource` などノードを値に持つ map の値は `Node`。

### 6.3 printer の単体等価 (`storeprinter`、新設)

corpus (storeparser の `TestCorpus` と同じ全 file) の各 file を Pointer (`parser.ParseSourceFile`) と Store で parse し、Pointer は `printer.NewPrinter(opts, printer.PrintHandlers{}, printer.NewEmitContext())`、Store は `storeprinter.NewPrinter(opts, …, storeprinter.NewEmitContextIn(region))` で次を印字して、**文字列が完全に一致すること。** writer は checker と同じ `printer.NewTextWriter(newLine, 0)` (checker/printer.go の `typeToStringEx` と同じ)。

**Store の側は、source と合成のノードが同じ program に属するようにする** (2026-09-29 のレビューで追加)。`storeparser.ParseSourceFile` は IDSpace が nil の Store を作るので、そこから region は作れず、別の IDSpace の region で作った合成ノードが source のノードを子に取ると `checkImport` (不変条件 26) が拒否する。file ごとに:

```go
space := store.NewIDSpace(1)
file := storeparser.ParseSourceFileIn(space, 0, opts, text, kind)
region := store.NewNodeRegion(space)
ctx := storeprinter.NewEmitContextIn(region)            // 印字の EmitContext
clones := ctx.Factory                                    // 3 の複製と §6.3 の EmitContext の fixture (Pointer も同じく印字の EmitContext の Factory)
```

1. **file の root**: `Write(root, file, writer, nil)`。
2. **file の中のノードを直接**: 全ての statement (入れ子を含む) と、全ての型のノード (`ast.IsTypeNode` が真のもの) と、全ての entity name を、それぞれ `Write(node, file, …)` と **`Write(node, nil, …)`** で印字する。checker は型のノードや entity name を、`enclosingDeclaration` が無ければ source file を nil にして直接印字する (checker/printer.go の `typeToStringEx` など)。**file の root を nil で印字しても nil の経路は通らない**: `emitSourceFile` が `currentSourceFile = node` を設定するので (printer.go:4670)、子の印字では source の text が使える (2026-09-29 のレビューで判明)。
3. **合成のノード**: 2 の型のノードと entity name を、印字する EmitContext の Factory (Pointer は `printer.NewEmitContext()` の `Factory`、Store は `ctx.Factory`) の `DeepCloneNode` で複製し、同じく source file あり / nil で印字する。nodebuilder が作る合成ノードの印字 (位置が合成、親が無い) の経路を checker 無しで通す。

- `opts` は checker/printer.go の 5 つ (`createPrinterWithDefaults`、`…RemoveComments`、`…RemoveCommentsOmitTrailingSemicolon`、`…RemoveCommentsOmitTrailingSemicolonNeverAsciiEscape`、`…RemoveCommentsNeverAsciiEscape`) と同じ設定。`…RemoveCommentsNeverAsciiEscape` には checker に呼び出し元が無い (使われるのは 4 つ) が、定義されている設定なので 5 つとも試験する。1〜3 の全部を 5 つの設定で行う。
- 片方だけが panic したら不一致。両方が panic したら一致として数え、数を (設定 × source file あり / nil × 1〜3 の種類) の cell ごとに報告する (cell が両方 panic で埋まっていれば、その cell は何も比べていない)。comment を残す `createPrinterWithDefaults` × nil は、printer が `currentSourceFile == nil` で comment を読まずに返る (printer.go:639・859・877・3070) ので `RemoveComments` × nil と同じ経路になる。表にそう注記する。
- `-short` では corpus を fixtures だけにしてよい。全 corpus の実行時間を報告する。
- **source file が nil の経路の試験** (2026-09-29 のレビューで追加): corpus の印字だけでは、nil に固有の分岐を通ったかは分からない (`canUseOriginalText` が false になるのは nil のときに限らない。例: corpus の parser.numericSeparators.decimal.ts の `1_000_000_000` は、5 つの設定の Target が 0 なので root の印字でも false になる)。そこで、**source file の引数だけを変えると Pointer の出力が変わる**入力を小さな fixture にして、両側の出力を期待の文字列で固定する。少なくとも: 識別子の escape (`type T = \u0061;` の型参照を印字すると、file ありは `\u0061`、nil は `a`。printer.go:241-248 の `canUseSourceFile`)、その識別子の `DeepCloneNode` の複製 (合成なので file ありでも `a`)。**元のノード**は、Pointer の file あり / nil の出力が違うこと (nil の分岐が効いていること。`\u0061` / `a`) と、Store がそれぞれに一致することを確かめる。**合成の複製**は位置が合成なので、Pointer はどちらも `a` を返す。複製には file あり / nil の両方で `a` を要求し、出力の差は要求しない (2026-09-29 のレビューで訂正)。ほかに Pointer で file の有無で出力が変わる経路が見つかれば足す。
- corpus の 2 と 3 について、Pointer の出力が file あり / nil で違った印字の数を数えて報告する (0 でもよい。nil の経路の保証は上の fixture が担う)。
- **EmitContext の情報の試験** (2026-09-29 のレビューで追加): 上の印字は EmitContext に何も書かないので、nodebuilder が EmitContext に書く情報の変換を確かめない。印字する EmitContext の Factory でノードを作り、次をそれぞれ設定した印字と設定しない印字を両側で行う: (1) **emit flags** (`EFNoAsciiEscaping` を付けた非 ASCII の文字列 literal。Pointer は付けると `"あ"`、付けないと `"\u3042"`)、(2) **textSource** (`NewStringLiteralFromNode` で source の literal や識別子から作った文字列 literal。printer.go:198・236)、(3) **original** (`SetOriginal` で source のノードを original にした合成ノード。comment を残す設定で、original の comment や位置を printer が読む経路)、(4) **合成の comment** (`AddSyntheticLeadingComment`)。**各項目で、Pointer の出力が設定のあり / なしで違う入力を選び**、期待の文字列で固定して Store が一致すること。出力が変わる入力が見つからない項目があれば、試験を省かずにそう報告する (その情報を printer が読む経路が checker の設定で無いのか、入力が足りないのかを分けて書く)。
- 報告: file 数、1〜3 と設定ごとの印字の数と不一致の数、最初の例。除外は置かない。

## 9. 本書で決めたこと (残りの設計に無いもの)

| 項目 | 決めたこと | 根拠 |
| --- | --- | --- |
| region と Factory | checker ごとに 1 つの region を `NewChecker` の P2 で作り、nodebuilder の EmitContext も同じ region。IDSpace は `Program` の P2 に足した `IDSpace()` から取る (file が 0 件の Program があるので先頭の file に頼らない) | Store の Factory は region が要り、Pointer の zero 値の factory を写せない。動作設計の「region は checker ごと、Factory は共有しない」 |
| `NewChecker` を P2 | 変換の出力と同じ本体 + region と Factory の 2 行 | region を作る場所が Pointer に無い。struct に field を足す規則は型から決まらない |
| storechecker / storeprinter の型は刈らない | 型の宣言は全部出し、関数と method だけ刈る | 型を刈っても得るものが少なく、刈り残しの判定を増やすだけ |
| interface の到達 | 到達した型が到達したコードの名指す interface を満たせば、その interface の method を全部到達とする | 代入があるとコンパイルに全 method が要る |
| 根に単体等価の入口を足す | printer の `NewPrinter` / `Write`、nameresolver の `Resolve` | §6.2 と §6.3 が呼ぶ。checker の根からも届く見込みだが、届かなくても単体等価を回せるように |
| nameresolver の単体等価の callback | 両側で同じ単純な callback。checker の lookup を真似ない | nameresolver の辿り方だけを比べる。checker の lookup は 2b |
| `File` の field の移行 | `FileName`・`Path`・`Text`・`Imports` を小文字の field + Pointer と同名の method にし、既存の読み書きを置き換える (§4.2) | 同名の method を足せず、`ast.HasFileName` を満たすには method が要る。`ast.NewHasFileName` で包む規則は呼ぶたびに確保し、`*store.File` の同一性も失う |
| printer の単体等価 | corpus の全 file の root、中の statement・型のノード・entity name、その合成の複製を、checker の 5 つの設定 × source file あり / nil で印字して完全一致 | checker 無しで printer の変換を確かめる (残りの設計 §2.4)。root だけでは nil の経路を通らない (§6.3) |
| List が `[]Node` に流れる箇所 (R4') | `Nodes()` のコピーを挿入する規則 (案 A)。`getEffectiveCallArguments` は P2 にしない | 2026-09-30 のユーザーの決定 (残りの設計 §3 の 5): まず動かし、性能は 2c の後で案 B / E を検討 |
