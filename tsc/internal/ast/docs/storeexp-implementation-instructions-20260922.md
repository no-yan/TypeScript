# storeexp 実装指示書

作成日: 2026-09-22。対象は実装を担当するエージェント。設計の根拠は [store-ast-design-20260922.md](store-ast-design-20260922.md) (以下「設計文書」)。検証の手順と判定は [storeexp-verification-instructions-20260922.md](storeexp-verification-instructions-20260922.md) (以下「検証指示」)。

設計判断はこの文書で済ませてある。書かれていない判断が必要になったら、実装を進めずに報告する。

## 0. 作るものの性格

**検証用の書き捨てである。** 設計文書 §4 の実験 E1〜E6、E10、E11 を測るためだけに作る。本物の Store AST ではない。

本物と違う点:

| | この実装 | 本採用された場合 |
| --- | --- | --- |
| Store の作り方 | Pointer AST から変換する | parser が直接構築する |
| generator | Go の小さなプログラム (`_gen/`) | `tools/scripts/tsc/generate-go-ast.ts` を直接変更する |
| 構築 | shape 駆動の汎用 builder | kind ごとの生成 constructor |
| typed view と slot 定数 | 代表 7 kind を手書き | 全 kind を生成 |
| data word | Identifier の text だけ | 全 kind の非 child member |
| 配置 | `tsc/internal/ast/storeexp/` | 未定。移行の設計で決める。この配置は本番の配置を意味しない |
| binder / checker / emit / LSP | 結合しない | 別設計 |

## 1. ガード (必須)

書き捨てのコードが後続の作業で無批判に拡張されるのを防ぐ。次をすべて満たすこと。

1. package は `tsc/internal/ast/storeexp`、package 名は `storeexp`。
2. `doc.go` 以外の全 `.go` ファイル (test、生成物を含む) の先頭に `//go:build storeexp` を置く。production のビルドからは import できなくなる。`_gen/main.go` は `//go:build ignore`。
3. `doc.go` (build tag なし) の package comment に次を英語で書く。リポジトリのコメントは英語なので合わせる。
   - これは実験であり production code ではないこと。
   - 目的 (設計文書 §4 の実験) と、設計文書・この指示書・検証指示へのパス。
   - 本物と違う点 (§0 の表の要約)。
   - **拡張の禁止**: 検証指示の実験に必要なもの以外を足さない。binder / checker / parser / emit / LSP との結合、全 kind の typed view、production package からの import を足さない。足す必要を感じたら設計文書に戻る。
   - **出口**: 検証レポートの後、ユーザーが削除か本採用かを決める。本採用は `generate-go-ast.ts` での再実装であり、この package の rename や移動ではない。
4. 生成物の 1 行目は `// Code generated by internal/ast/storeexp/_gen (EXPERIMENT). DO NOT EDIT.`。
5. `storeexp` の外のファイルを変更しない。`ast.json`、`generate-go-ast.ts`、`internal/ast` の既存コードに触らない。

## 3. 型と API (`store.go`)

設計文書 §2.1、§2.3、§2.5 のとおり。名前と形を変えない。

```go
type NodeRef uint32 // index into Store.nodes; dense; 0 = nil

type NodeHeader struct { // 24 bytes, no pointers
	kind          ast.Kind
	modifierFlags uint16 // syntactic ModifierFlags, bits 0-15 only
	flags         ast.NodeFlags
	pos, end      int32
	parent        NodeRef
	data          uint32 // start of the payload in Store.extra; Identifier: see Text
}

type Store struct {
	nodes []NodeHeader // nodes[0] is a sentinel: kind Unknown, parent 0
	extra []uint32     // child slots, list blocks; extra[0] == 0
	src   string
	texts string // texts that are not a substring of src
	file  uint32
}

type Node struct { s *Store; h *NodeHeader }
type Ref  struct { file uint32; id NodeRef }
```

- `unsafe.Sizeof(NodeHeader{}) == 24` をテストで固定する。
- **`modifierFlags` の宣言に TODO コメントを必ず置く。** 内容: bit 16 以降 (Deprecated、JSDoc 系 bit 23-27、`HasComputedJSDocModifiers`、`HasComputedFlags`) は header に入れない。別経路は未設計で、JSDoc の置き場所と一緒に決める。設計文書 §2.1 と §7 を参照先に書く。`ModifierFlags` を `uint16` に切り詰める箇所 (Builder) にも同じ趣旨の TODO を置く。
- `func (s *Store) node(ref NodeRef) Node { return Node{s, &s.nodes[ref]} }`。nil 分岐を入れない (`nodes[0]` が番兵)。
- header の読みは `Node` のメソッド: `Kind()`、`Flags()`、`Pos()`、`End()`、`ModifierFlags() ast.ModifierFlags`、`Parent() Node`、`IsNil() bool` (`h.kind == ast.KindUnknown`)。`s.Kind(ref)` のような「ref を受けて field を返す」accessor を作らない (budget 文書 規則 1)。
- `func (n Node) Ref() NodeRef` は `h` と `nodes` の base の差から逆算する (`unsafe` を使ってよいのはここだけ)。
- accessor の中に nil ガード、kind 検査を置かない。kind 検査は `const storeChecks = false` で囲んだ assert だけ (budget 文書 規則 5)。テストは `storeChecks` を true にした場合も通ること (build tag `storechecks` で切り替える)。

### list

```go
type List struct { s *Store; at uint32 } // at = index of the block in extra; 0 = nil list
// block: [len, pos, end, elem0 ... elem(len-1)]
func (l List) IsNil() bool
func (l List) Len() int
func (l List) Pos() int32
func (l List) End() int32
func (l List) Refs() []NodeRef   // contiguous view, no allocation
func (l List) At(i int) Node
```

`Refs()` は `extra` の部分列を `[]NodeRef` として返す。`[]uint32` からの変換に `unsafe.Slice` を使ってよい。

### Builder

構築は計測対象外なので、shape 駆動の汎用 builder 1 本でよい。

```go
func NewBuilder(src string, file uint32) *Builder
func (b *Builder) List(pos, end int32, elems []NodeRef) uint32           // returns block index
func (b *Builder) Node(kind ast.Kind, flags ast.NodeFlags, mod ast.ModifierFlags,
	pos, end int32, slots []uint32) NodeRef                              // slots per shapes[kind]
func (b *Builder) Identifier(flags ast.NodeFlags, pos, end int32, text string) NodeRef
func (b *Builder) Finish() *Store                                        // exact-size copy; no renumbering
```

- `Node` は payload を `extra` に追記し、header を追記し、**子の `parent` を書く** (child slot は `nodes[slot].parent = id`、list slot は block の全要素)。本実装では生成 constructor が同じことをする (設計文書 §2.7)。
- id で書く。構築中に `*NodeHeader` を保持しない。
- `Finish` の後にだけ `Node` を配る。

### text (実験での仮決め)

- Identifier は `data` = text の開始 offset、`Text()` は `s.src[h.data:h.end]`。変換器は `src[end-len(text):end] == text` のときこの形にする。
- 一致しない場合は `texts` に追記し、`extra` に `[off, len]` の 2 word を置き、`data = 1<<31 | extra の index`。`Text()` は最上位 bit で分岐する。
- flag の置き場所は設計文書 §7 で未決。この仮決めをコメントに明記する。
- Identifier 以外の kind の text と data word は置かない (範囲外)。

## 4. generator (`_gen/main.go`)

入力は `tools/scripts/tsc/ast.json` (読むだけ) と、`golang.org/x/tools/go/packages` で読んだ `internal/ast` の型情報。実行は `cd tsc && go run internal/ast/storeexp/_gen/main.go`。

1. `nodes.definitions` の各定義について、`members` を宣言順に見る。Go の struct `*ast.<定義名>` に対して `types.LookupFieldOrMethod` で member 名の field を引き、型で分類する。
   - `*ast.Node` (alias を含む) → child slot
   - `*ast.NodeList`、`*ast.ModifierList` → list slot
   - `[]*ast.Node` (`list: "raw"`) → list slot。block の pos / end は 0
   - それ以外 → slot にしない
2. kind → shape。`kind` が配列の定義 (TypeAliasDeclaration など) は全 kind に同じ shape を与える。定義の無い kind (token、keyword) は slot 0。
3. `handWritten` の SourceFile と `handWrittenVisitor` の JSDocParameterOrPropertyTag は generator 内の override 表で与える。Pointer 版の手書き `ForEachChild` (`internal/ast/ast.go`) と同じ子・同じ順にする。
4. §7 の fingerprint テストが合わない kind が出たら、Pointer 版の `ForEachChild` を読んで override 表に足す。accessor や walker の側で特別扱いしない。

出力:

- `shapes_generated.go`
  ```go
  type shape struct { slots uint8; listMask uint16 } // bit i: slot i holds a list block index
  var shapes [512]shape
  var nameSlot, expressionSlot, typeSlot, initializerSlot, bodySlot [512]uint8 // 0xFF = absent
  ```
  多相表は、その名前の member (`name` / `Expression` / `Type` / `Initializer` / `Body`) を持つ kind の slot 番号。§7 の等価テストで Pointer 版の `Name()` などと一致しない kind は override で直す。
- `foreach_generated.go`: `func (n Node) ForEachChild(v Visitor) bool`。slot を持つ全 kind を **Kind の数値順に並べた 1 本の switch** にし、各 case は kind 別の関数を呼ぶ。kind 別の関数は slot ごとの直線コード (child: 0 でなければ `v(s.node(ref))`、list: block を走査)。`type Visitor func(Node) bool`、true で打ち切り (Pointer 版と同じ契約)。
- `convert_generated.go`: `func Convert(file *ast.SourceFile, fileIndex uint32) *Store`。post-order で子を先に変換し、kind ごとに member を読んで `Builder.Node` を呼ぶ。private な member (`name`、`modifiers`) は公開 accessor (`Name()`、`Modifiers()`) で読む。読めない member があれば generator が一覧を出して失敗する。JSDoc は Pointer 版の `ForEachChild` が辿らないので変換しない。

## 5. 手書きの accessor (`views.go`)

「生成されるはずの出力の見本」として書く。slot 番号は名前付き定数にし、値は `shapes_generated.go` と食い違わないことをテストで固定する。

代表 7 kind: token (view なし、header だけ)、Identifier、BinaryExpression、CallExpression、PropertyAccessExpression、FunctionDeclaration、SourceFile。設計文書の 6 kind に PropertyAccessExpression を足した。`Name()` と `Expression()` の最多の receiver (44.6%、46.3%) だからである。

```go
type CallExpression struct { s *Store; h *NodeHeader }
func (n Node) AsCallExpression() CallExpression { return CallExpression(n) }      // no load
func (c CallExpression) Expression() Node      { return c.s.node(NodeRef(c.s.extra[c.h.data+callExpressionSlot])) }
func (c CallExpression) Arguments() List       { return List{c.s, c.s.extra[c.h.data+callArgumentsSlot]} }
```

- 子を返す accessor は解決済みの `Node` を返す。list は `List` を返す。
- view の作成時に何も読まない。slot をまとめて読む struct を作らない。
- 多相 accessor: `func (n Node) Name() Node` は `nameSlot[n.h.kind&511]` を引き、0xFF なら `n.s.node(0)` を返す。`Expression()`、`Type()`、`Initializer()`、`Body()` も同じ形。switch を書かない。
- `func (n Node) Text() string` は §3 のとおり (Identifier 以外は範囲外。`storeChecks` で assert)。

## 6. walker (`walk.go` と test 内)

- `ForEachChildShape(v Visitor) bool`: `shapes[kind&511]` を引いて slot を順にループする版。設計文書 §8 の最適化候補で、表はすでにあるので一緒に測る。
- ベンチ用 walker は Pointer 版 (`internal/ast/ast_benchmark_test.go` の `astWalker`) と同じ形にする。callback は計測前に 1 回だけ束縛し、訪問ごとの仕事は `visits++` だけ。

## 7. テスト (`store_test.go`)

入力は `fixtures.ASTBenchFixtures` (checker.ts、dom.generated.d.ts) と、`internal/ast/ast_benchmark_test.go` の small source。

1. **fingerprint**: Store を preorder で辿り、`kind|pos|end` の列の sha256 と訪問数が `astBenchmarkBaselines` の値と一致すること (リテラルを出どころのコメント付きで写す)。`ForEachChild` と `ForEachChildShape` の両方で。
2. **small walk**: `TestASTBenchmarkSmallWalk` と同じ source で同じ `[]astVisit` リテラルになること。
3. **等価**: Pointer と Store を同時に preorder で辿り、全ノードで次が一致すること。kind、pos、end、flags、`ModifierFlags() & 0xFFFF`、親の kind と pos、`Name()` (kind、pos。不在は両方 nil)、`Expression()` / `Type()` / `Initializer()` / `Body()` (Store の表が 0xFF でない kind だけ)、Identifier の `Text()`、代表 kind の全 accessor、list の `Len()` / `Pos()` / `End()` と各要素。
4. `Node.Ref()` の往復 (`s.node(n.Ref()) == n`)、`unsafe.Sizeof(NodeHeader{}) == 24`、slot 定数と `shapes` の整合。
5. 全テストを `-tags storeexp` と `-tags 'storeexp storechecks'` の両方で通す。

## 8. ベンチ (`bench_test.go`)

`runtime.GC()` 後に 1 回空回ししてから測る。入力の parse と変換は計測外。KPC 版は `kperf.Start` / `session.Measure` / `session.Report` を `BenchmarkASTWalkKPCV1` と同じ形で使う。

**Walk**

- `BenchmarkStoreExpWalkV1/<fixture>/{pointer,switch,shape}`: `visits/op` と `ns/visit` を報告。`pointer` は同じ process 内の対照 (`astWalker` と同じコード)。
- `BenchmarkStoreExpWalkKPCV1/{pointer,switch,shape}`: checker.ts。

**Access** (`BenchmarkStoreExpAccess` と `BenchmarkStoreExpAccessKPC`、checker.ts)

事前に preorder の `[]*ast.Node` と `[]Node` を作る。対象を絞る操作は絞った後の slice を作る。各操作は結果を `uint64` に足し込み、Pointer と Store で合計が一致することを計測外で確認する。`ops/op` (アクセス回数) を報告する。sub-benchmark 名は `<操作>/{pointer,store}`。

| 操作 | 対象 | 1 回の内容 |
| --- | --- | --- |
| `baseline` | 全ノード | slice の要素を読むだけ (ループの固定費。差し引き用) |
| `header` | 全ノード | kind + flags + pos + end (親は `parentChain` で別に測る) |
| `known` | CallExpression と BinaryExpression と PropertyAccessExpression | cast して子の kind を読む: `Expression`、`Left` + `OperatorToken` + `Right`、`Expression` + `Name` |
| `polyPresent` | `Name()` が nil でないノード | `Name()` の kind |
| `polyAll` | 全ノード | `Name()` の kind (不在は 0)。不在の経路の単価 |
| `list` | CallExpression | `Arguments` の全要素の kind の和 |
| `text` | Identifier | `len(Text())` + 先頭 byte |
| `modflags` | 全ノード | `ModifierFlags()` |
| `parentChain` | Identifier | 親を root まで辿って段数を数える |
| `refRoundTrip` | 全ノード (Store のみ) | `Ref()` |

各操作の本体は `opHeaderPointer(n *ast.Node) uint64`、`opHeaderStore(n Node) uint64` のような名前付き関数にし、ベンチのループからはそのまま呼ぶ (inline される)。命令列を読むために、同じ本体を呼ぶだけの `//go:noinline` のラッパ `asmHeaderPointer` / `asmHeaderStore` … を `asm_test.go` に置き、テストから 1 回ずつ呼んで link に残す。ラッパはベンチでは使わない。

Pointer 側は現行の公開 API をそのまま使う (`n.Kind`、`n.Parent`、`n.AsCallExpression().Expression`、`n.Name()`、`n.Text()`、`n.ModifierFlags()`)。ベンチのために Pointer 側を速く書き直さない。

**Footprint**: `TestStoreExpFootprint` が fixture ごとに `len(nodes)*24`、`len(extra)*4`、合計の B/node を `t.Log` する。
