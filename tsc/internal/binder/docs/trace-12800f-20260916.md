## 仮説と提案する最小変更

入口は `binder.go:1382`。現在は flags・診断状態を確認した後、通常識別子にも `TextAt → scanner.GetIdentifierToken → textToKeyword` を実行する。

その後に診断を行うのは future-reserved の9語と await だけである。

`implements / interface / let / package / private / protected / public / static / yield / await`

これらだけを既存の `ast.Kind` に分類する局所 switch とし、それ以外を return する案を第一候補にする。既存の `IsIdentifierName`、ambient/JSDoc、file diagnostics、module/top-level、await/yield context、および診断の条件順は保つ。とくに現行では yield が future-reserved 範囲にも含まれるので、条件順を変更しない。

これは汎用 scanner 全体の置き換えではない。map のハッシュ計算と、診断対象外の contextual keyword への親/name query を省けるという仮説。追加の分岐やコードサイズは増えるので、3.48〜4.33%がそのまま速度向上になるとは主張しない。7.21〜8.15%全体を削れるとも扱わない。

## 次点

1. `declareModuleMember` (`binder.go:433–434`) の local/export symbol 作成で、同じ宣言の名前・default modifier を二度解決する部分を共有する。`declareSymbolEx:167–178`、`getDeclarationName:324`、`Handle.ModifierFlags` (`store_query_manual.go:226`) が対象。local 名と export default 名の違い、衝突診断、computed/private/anonymous 宣言を保つ必要があり、第一候補より変更面が広い。26%近い宣言全体をこの重複だけに帰属しない。試すなら既存 export-heavy unique declaration micro を入口にするが、synthetic は方向確認のみ、実入力 bind を採用根拠とする。
2. `bindEachChild` (`binder.go:1783`) は呼出元が保持する kind を再取得している。小さい削減候補だが、inline 展開のため単独の sample 帰属はなく、今回の trace だけでは有用な改善幅を確定できない。過去の kind-hoist の timing も未解決なので、同じ探索を広げるより第一候補を先に検証する。

`bindEach` と functions-first の span 利用は現行で復元済み。旧計画の「span を戻す」を未実施の次候補として再提案しない。parse-time reserved identifier フラグや永続 keyword cache は parser/factory/clone の整合性・メモリ費を増やすため、この局所案の後に判断する。

## Allocation drivers と GC

CPU stack からは Symbol table の挿入・成長、Symbol arena、Flow chunk、`PrepareBindTables` の列確保、Locals map、単一 declaration 用 Handle arena が見える。`mallocgc*` family が祖先にある sample の合計は phase の約12.78% / 14.30%。これは割り当て処理を含む CPU 寄与であり、allocation のバイト数や回数ではない。

`wbBufFlush*` の祖先を持つ sample は約8.97% / 2.01%、`gcAssistAlloc*` は約0.18% / 1.89%。GC の発生状況が異なるため、二つの trace の差を最適化効果とは読まない。background GC は binder ancestry を持たないので、この分母には含めていない。最初の switch 候補は主にCPU削減で、B/op・allocs/op削減を約束しない。

## 性能評価前に解消すべき正確性の問題

今回の source 照合で HEAD の別 node kind 再利用を2件確認した。source の静的確認と UUID 一致 binary の逆アセンブルによる確認であり、実行テストはしていない。

- `binder.go:701 → 1482`: label 自体の kind を渡しているが、`checkStrictModeLabeledStatement` の switch に必要なのは `statement.Statement` の kind。現行の call site では診断対象 case に入れない。以前の子 statement の kind 取得を戻す必要がある。
- `binder.go:2249`: call expression の kind を SuperKeyword と比較しており常に不一致。`IsDottedName` は SuperKeyword に true を返すため、`super()` に以前は作らなかった FlowCall が作られる。callee expression の kind を比較する必要がある。

これらを含む版を正しい性能基準として採用しない。今回の調査では修正していない。

## 再現と受入条件

解析の再現は保存した XML と SQLite を使う。元データを再展開する場合は次の通り。

```sh
xcrun xctrace export --input "$TRACE" --toc --output toc.xml
xcrun xctrace export --input "$TRACE" --xpath '/trace-toc/run/data/table[@schema="cpu-profile"]' --output cpu-profile.xml
```

`TRACE` は上記 trace 絶対パス。解析スクリプトと SQLite の schema は artifact set に保存した。新規 capture は不要。

次の検証単位は正確性修正と局所 switch を分け、以下とする。

1. キーワード全件と非キーワードで旧実装の「診断対象となる分類」と一致することを確認する。予約語を property/import/export/JSX 名に使う場合、escaped identifier、strict/module、await/yield の診断・順序・span を検証する。
2. 修正済み baseline と候補を固定し、既存の寿命安全な実入力 bind ハーネスで checker.ts と宣言入力から対照を取る。raw の `ns/op`、`B/op`、`allocs/op` を保存して `benchstat old.txt new.txt` で比較する。命令数と wall timing の不確実性は別に評価する。
3. 変更コストに見合う再現可能な削減を確認する。固定3%を採用下限としない。small switch でもコードサイズ・分岐・他入力の退行を確認し、最終的には代表 CLI／parse+bind の累積結果を評価する。
